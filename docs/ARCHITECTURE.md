# 架构与数据结构

## 请求路径

浏览器与 FastAPI 同源，无跨域开放。静态前端通过 Cookie 会话调用 /api。身份依赖从数据库查询有效会话及活跃账号，写请求另验证 CSRF；权限依据数据库中的角色／门店／岗位／吧台，不信任客户端自报身份。

检索顺序：确认所选吧台属于员工 → 按门店筛选知识 → 匹配岗位和吧台 → 获取当前版本 → 名称及别名匹配 → 原文卡片返回。索引范围和权限不能依赖未来接入的大模型过滤。

## 表映射

| 表 | 用途与关联 |
| --- | --- |
| users | 账号、密码散列、角色、门店、岗位、允许吧台、活跃状态 |
| sessions | 仅保存随机令牌的 SHA256、账号、CSRF 与到期时间 |
| login_limits | 登录失败限流窗口，不保存明文账号／地址键 |
| documents | 知识系列：门店、名称、类型、岗位、吧台、别名、高风险标记 |
| revisions | 关联知识系列；版本、状态、结构化正文、来源、生效／失效、创建和批准人员 |
| queries | 员工提问、门店／吧台、引用版本编号集合、是否匹配、时间 |
| feedback | 关联原始提问与反馈人，反馈类型、描述、处理状态及结果 |
| modules | 培训标题、目标、固定资料版本集合、测验题及正确答案、通过线 |
| assignments | 模块与员工唯一对应；分配人、最佳成绩、实操确认人／时间／描述 |
| attempts | 每次测验成绩及时间；不保存每道题的作答明文 |
| audit | 门店、操作者、动作、对象与时间 |

字段与约束的权威定义见 app/schema.sql；JSON 列的输入由 Pydantic 验证，SQL 全部参数绑定。

## 版本规则

草稿 draft → 待审核 review → 发布 published → 停用 retired。

已发布不代表已经生效。读取时在生效时间不晚于当前时间的已批准版本中取最大版本号，然后检查是否停用／到期。不向更早版本回退，避免已撤回的标准复活。未来版本尚未生效时，当前版本仍可查询。审批时间统一存 UTC，网页显示北京时间。

数据库触发器禁止覆盖已批准版本正文、来源、版本号、生效／失效时间、创建者及批准记录；允许将状态变为 retired。发布新版本使用同一知识系列，新版本号在 BEGIN IMMEDIATE 事务内分配；(document_id,version) 唯一。

岗位与吧台范围属于知识系列，同系列新版本不得变更范围、标题、类型和别名。迁移范围时需要新知识系列，并主动停用旧版本。此限制避免权限变更使旧版本意外暴露。

## 培训规则

模块明确绑定 revision_ids；分配时校验目标员工有权查看且材料仍然有效。阅读、测验、实操验收时再次校验。题目的正确答案只返回主管，员工端不返回。测验成绩由服务器计算并记录最佳分；必须达标且由其他主管现场确认后记录实操通过。资料更新后任务失效，不自动转换为新版本学习完成。

## 部署演进

1. 本地单店验证：SQLite 与同源网页，优先验证标准和管理流程。
2. 门店小范围试点：TLS 反向代理、持久化卷、数据库备份恢复、真实账号、限流和保留期限执行；先完成现场验收。
3. 资料量增加后：文档解析与审批工作流、全文／中文检索、版本内容的检索索引。
4. 基于评测再加入 Embedding 与 Reranking；检索必须先应用有效版本与权限过滤。
5. 最后接入 LLM，只依据证据组织回答，配方数字仍由数据库直接渲染；检索无证据拒答。模型 API Key 仅放服务端环境变量。
6. 多实例或多租户前迁移 PostgreSQL、迁移管理、集中限流与权限回归，避免将单机 SQLite 直接共享给多个写实例。

先把门店资料和测试集做好，再选择具体向量库与模型，避免当前就引入没有验证价值的运维负担。
