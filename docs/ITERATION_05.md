# 迭代05：HQ / Agents 与多门店权限

日期：2026-11-21（北京时间）；版本：0.6.0。

## 完成范围

| 模块 | 已实现 |
| --- | --- |
| HQ 连锁总部 | 独立租户与门店登记、到期跨店授权／撤销、门店上下文切换、双向确认的独立门店迁入、总部模板版本／审批／分发、门店差异和签收、签收后本店草稿、真实生效状态 |

当前没有接入第二家真实门店。本轮完成的是可配置和可测试的多门店实现；多租户安全、迁移和业务闭环在隔离数据库验证，不等于真实连锁试点已验收。

## HQ 使用顺序

1. 旧库升级后，原门店编号、账号与业务记录保持不变；每个既有门店成为一个独立租户，不能因为使用同一数据库就推断属于同一连锁。各门店首个有效管理员成为该独立租户的初始总部负责人。
2. 总部负责人在HQ查看自己的租户标识。登记新门店时填写门店负责人确认资料，设置首个岗位、吧台标识。登记不自动提供业务访问权。
3. 在“明确跨店授权”选择本租户人员、目标门店、角色、岗位、吧台、到期时间和依据。访问目标业务须显式授权，即使是总部负责人也如此。
4. 页面顶部选择已授权门店；后端每次请求重新核对租户和有效授权，不信任前端自报角色。授权撤销、到期或变更立即影响后续请求。可随时点击“返回本店”，账号退出和改密不依赖已失效的跨店授权。
5. 如已有门店在独立租户：由原单店负责人填写目标总部租户标识申请整店迁入，再由目标总部负责人确认。当前只支持独立单店租户完整迁入，不拆分现有多店连锁。
6. 迁入时在一个事务中改变门店归属、撤销该店旧授权和旧总部身份、撤销该店人员会话。业务门店编号不变，知识、库存、报表、培训、Flow、账号和历史记录保留；员工重新登录。新总部访问业务仍需显式跨店授权。
7. 从本店已批准知识建立总部模板草稿，提交并人工批准。模板支持配方、SOP、规则和三类服务内容；配方／高风险资料须明确确认。新版本保留模板标题和类型，已提交版本不覆盖。
8. 分发指定批准版本到本租户门店。请求带幂等编号，同一版本／门店只创建一条发布记录，不直接改动门店知识。
9. 门店主管在本店上下文签收，确认岗位／吧台范围；如修改原料、步骤或服务内容须明确写差异原因。采用后仅生成本店草稿，仍走原审核发布流程。
10. 总部同时看到“已签收”和“本店草稿／待审核／待生效／已生效”等状态，签收不等于标准已经生效。门店采用较新模板后，不能再回退签收旧版。

跨店身份同时用于人员选择、培训分配、理论考试、实操验收、变更重学、技能证据、Flow和业务待办，不把账号原籍门店改成目标门店。

## Agents 使用顺序

1. 主管在Agents选择本店已授权配方版本、吧台、预计上市时间和初始负责人，生成规则式计划草稿。
2. 固定七项为：标准审核、SKU／单位／成本、实物盘点、服务与客诉、理论与实操培训、设备及当班准备、店长最终确认。负责人逐项核对实际记录，缺失依据不自动补成事实。
3. 草稿可调整七项任务的负责人和截止时间并记录说明。任务不可任意扩展为工具指令，截止须晚于现在且不晚于上市时间。
4. 提交后由主管明确批准或退回。审批、编辑使用计划序号防止覆盖并发变化。当前允许发起主管自己明确审批，与原知识流程保持一致，不是强制双人审批。
5. 批准后再次确认执行，只调用允许的create_launch_todos业务工具。它与人工新建待办共用后端函数、负责人和吧台校验、事务及审计。
6. 配方正文、状态、来源或有效版本发生变化时，执行会被阻止，须重新生成并审批；负责人失活、授权变化或期限失效也会阻止整次执行，不留下部分待办。
7. 重复请求按操作者／当前门店／动作／幂等编号和内容哈希返回原结果；编号用于不同内容会被拒绝。不同编号重复执行同一计划也返回原待办，不重复创建。
8. 工具审计记录请求哈希、计划、操作者、成功／幂等重放／阻止及说明。授权范围内的失败执行单独保存失败审计，不能因为事务回滚而丢失。
9. 员工在Agents查看自己的待办，提交事实和证据后完成。主管在Agents和Command跟进；完成待办不自动发布配方、改变库存、确认培训资格或宣布已具备上市条件。

当前不调用大模型，没有模型API费用；“智能代理”是受约束的固定计划与工具执行流程。没有通用工具运行器、浏览器操作、任意HTTP／Shell、自动采购、外部消息或自主发布。

## 租户与迁移规则

- 增量迁移版本5增加tenants、stores、hq_members、store_grants、store_transfers、hq_templates、hq_deliveries、hq_adoptions、work_tasks、agent_plans、business_requests、agent_tool_events。
- 旧业务的store字段保留，stores将门店连接至租户。所有业务请求先解析账号本店和目标门店，再核对同租户且明确授权，最后使用目标角色／岗位／吧台应用原业务隔离。
- X-BarOS-Store只选择上下文，不授予权限；会话身份、CSRF和角色来源仍为数据库。跨租户或未授权门店上下文返回403，按记录ID跨租户访问返回404。
- 迁入申请需要原负责人主动发起且目标负责人接受；处理时再次检查原单店结构、申请人权限与门店归属，变化后不继续迁移。
- 跨店授权只能面向本租户有效人员；角色、岗位、吧台明确填写并设置期限。人员原籍门店不变，租户并入后原总部身份不自动升级为新总部负责人。
- 账户名仍为当前实例全局唯一；这是现有SQLite单实例架构中的多门店实现，不等同于已完成公网SaaS安全审计或多实例改造。
- 既有单店没有管理员时不会自动授予普通员工总部权限；需由现有管理员恢复流程处理账号。

## 业务和工具边界

- 总部模板分发与签收都保留版本和范围。总部批准不绕过本店审核，门店差异有明确记录，重复签收不能覆盖原内容。
- 代理只会创建待办；计划文本不是对库存、成本、客流或经营表现的预测。配方原文来自指定资料版本，不进行大模型扩写。
- SQLite BEGIN IMMEDIATE内执行幂等检查与全部任务创建，并发重试也只生成一组任务。
- 保存的业务事实、既有财务报告和课程证据不因新增HQ或代理而改写。
- 当前不提供通用组织权限设计器、自动多门店数据复制、单店拆分迁移、跨租户直接授权或任意工作流／工具设计器。

## 验收边界

- 总部登记、迁入、签收、批准和待办生成均在隔离测试数据库验证；没有自动创建“第二家真实门店”，没有迁移或改写本地真实门店数据库。
- 真实浏览器连接本轮启动失败；DOM／表单测试不能证明真实点击、焦点、窄屏或店内操作已验收。
- 在真实连锁试点前须用第二门店的负责人、真实资料、岗位吧台、权限和迁移备份演练实际验收。代码就绪不替代这项业务前提。
